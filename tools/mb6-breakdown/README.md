# Разбор обязательных видов по одной МО

Форма для методолога: какие виды СЭМД матрица применимости считает обязательными
для конкретной медорганизации, по какому условию и регистрируются ли они.

Заведено 25.08.2026 под вопрос ГБУ «Межрайонная больница № 6», но к организации
не привязано — сгодится для любой, у которой цифра вызовет спор.

## Зачем

ВКС 24.08.2026, методолог: «50 видов из 145 регистрирует — да, это правда,
так оно и есть. 81 вид для неё является обязательным — ну, вот это уже неправда.
Поменьше, поменьше».

После применения перечней МО стало 82, а не меньше: перечни сузили состав
у других организаций, а у МБ № 6 виды, лежавшие в «не определено», перешли
в обязательные. Спорить цифрой бессмысленно — нужен список, по которому она
скажет, какие виды лишние и почему.

## Как устроена форма

Два листа.

**«Обязательные виды»** — все обязательные, сгруппированные по условию
применимости, с колонкой «Решение» (выпадающий список «оставить / убрать»)
и «Комментарий». Группировка не для красоты: если у больницы нет лицензии
на медосмотры, снимаются сразу девять видов, и отмечать каждый по отдельности
не нужно.

Ниже справочно перечислены виды в состоянии «не определено» — в обязательные
они не входят, но объясняют, почему число не сошлось с ожидаемым.

**«Свод по условиям»** — сколько видов держит каждое условие и сколько из них
регистрируется. Это главный лист для разговора: условие, дающее девять видов,
из которых ни один не регистрируется, — первый кандидат в лишние, и виден он
здесь, а не в списке из восьмидесяти двух строк.

## Как получить данные

Запрос к стенду. `PERIOD` — идентификатор рабочего периода, `OID` — организации.

```sql
SELECT t.nsi_oid AS code,
       t.name,
       r.requirement_status AS status,
       r.reason,
       r.source_name,
       COALESCE(f.document_count, 0) AS docs
FROM reporting_organization_semd_requirements r
JOIN reporting_semd_types t ON t.id = r.semd_type_id
LEFT JOIN reporting_remd_facts f
       ON f.semd_type_id = r.semd_type_id
      AND f.organization_oid = r.organization_oid
      AND f.period_id = 'PERIOD'
      AND f.scope_level = 'organization'
WHERE r.organization_oid = 'OID'
  AND r.requirement_status IN ('required','unknown')
ORDER BY r.requirement_status DESC, t.nsi_oid::int;
```

Выгружать в TSV:

```
docker exec axel_server_ready-app-db-1 psql -U telemed -d telemed_app \
  -A -F$'\t' -c "<запрос>" > mb6.tsv
```

## Запуск

```
python build_breakdown.py mb6.tsv "ГБУ «Межрайонная больница № 6»" out.xlsx
```

## Что стоит знать

**Условие берётся из основания, а не из формы напрямую.** Основание выглядит
как «Обязателен по матрице применимости (строка 28: Амбулаторный · наличие
прикрепленного населения)» — группировка идёт по части после двоеточия.
Если в основании несколько строк формы, берётся первая: группировка нужна
для укрупнения, а не для точности до строки.

**Группа «условия в форме нет».** Это не сбой разбора, а состояние самой формы:
у строки не задано ни типа подразделения, ни условия, и вид становится
обязателен всем 37 МО. У МБ № 6 таких два — виды 354 и 361, оба вынесены
методологу отдельными вопросами.

**`source_name` в выгрузке может быть кракозябрами** у импортов, сделанных
до 25.08.2026: имя файла тогда разбиралось только из UTF-8, а не из CP1251.
В форму эта колонка не попадает.
